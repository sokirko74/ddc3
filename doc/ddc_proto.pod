## Header

=pod

=head1 DDC SERVER PROTOCOL

This manual page describes the network protocol used by the DDC
(sub)corpus and distributed servers.  In the syntax descriptions,
the string "\x01" represents a literal ASCII byte with decimal value 1
(a.k.a. "SOH" a.k.a "start of heading"),
and " " represents a literal space character (ASCII byte with decimal value 32).

=cut

## Synopsis
=pod

 LENGTH DATA

 ##=====================================================================

 ##=====================================================================
 ## Leaf-Server Messages
 
 get_first_hits " " QUERY "\x01 " TIMEOUT " " LIMIT
 get_hit_strings " " FORMAT "\x01" OFFSET " " LIMIT
 

=cut

## Description
=pod

=head1 DESCRIPTION

This section contains descriptions of the various requests which may
be sent to a DDC server and their expected responses.

=cut

##==============================================================
## Generic Message Format
=pod

=head2 Generic Message Format

 LENGTH DATA

All messages sent to or from a DDC server share the common generic format C<LENGTH DATA>,
where C<LENGTH> is a 32-bit little-endian unsigned integer,
and C<DATA> is the underlying message data, which is exactly C<LENGTH> bytes long.

=cut

##==============================================================
## Common Messages
=pod

=head2 Common Messages

This section describes the messages accepted by all DDC servers.

=cut

##--------------------------------------------------------------
=pod

=head3 version

 version

Returns the version number of the
running server
as a string, by convention of the form
C<MAJOR.MINOR.MICRO-PATCHLEVEL>
where C<MAJOR>, C<MINOR>, and C<MICRO> are unsigned decimal integers,
and C<-PATCHLEVEL> is an optional string suffix.
This should be the same string reported by B<ddc_daemon> on startup.

Since v2.0.18

=cut

##--------------------------------------------------------------
=pod

=head3 status

 status
 status TIMEOUT

Returns status information on the running server as a JSON object of the form:

 {
  "name":"server",			//-- distributed server name
  "version":"2.0.18-pre1",		//-- distributed server version
  "hostname":"www.dwds.de",		//-- distributed server hostname if available (>= v2.0.35)
  "hostaddr":"127.0.0.1",		//-- distributed server socket hostname or address ("host" for ddc < v2.0.35)
  "port":50011,                         //-- distributed server socket port
  "started":"2014-02-17T13:49:59Z",	//-- ISO-8601 timestamp of last server start
  "uptime":1392644999,			//-- server instance uptime in seconds
  "nrequests":21,			//-- number of served requests
  "memkb":18756,			//-- memory resident set size in kb (>= v2.0.49, linux only)
  "cachesize":42,			//-- size of query cache (leaf servers only)
  "curlcachesize":24,			//-- size of curl cache (leaf servers only)
  "corpora":["corpus1","corpus2",...]	//-- registered subcorpus names (branch servers only)
 }

Very fast turnaround, since all returned data is known to the distributed server itself,
and no subcorpora need to be queried.

Since v2.0.18,
optional TIMEOUT parameter since v2.0.47.

=cut

##--------------------------------------------------------------
=pod

=head3 vstatus

 vstatus
 vstatus TIMEOUT

Like the C<status> command, but the elements of the returned "corpora" list for a branch server
are the JSON objects returned by the C<status> command to the associated subcorpus servers,
rather than just subcorpus names.
If the optional TIMEOUT parameter is specified, it should be an integer value indicating the
maximum time (in seconds) to wait for subcorpus responses; default=10.

Since v2.0.18,
optional TIMEOUT parameter since v2.0.47.

=cut


##--------------------------------------------------------------
=pod

=head3 info

 info
 info TIMEOUT

Returns information about associated corpora as a JSON object.
For a leaf server, the returned object is of the form:

 {
  //-- basic information
  "name":"corpus1",			//-- subcorpus name
  "version":"2.0.18-pre1",		//-- subcorpus server version
  "project":"corpus1",			//-- project basename
  "indexed":"2014-02-17T13:49:56Z",	//-- index timestamp (mtime of PROJECT._con)
  "nfiles":4,				//-- number of successfully indexed files
  "nsources":4,                         //-- number of source files (including empty and erroneous files)
  "nmasked":0,                          //-- number of "masked" (blacklisted) files in PROJECT._masked
  "ntokens":56294,			//-- number of indexed tokens
  //
  //-- global index options (see ddc_opt(5))
  "lang":"German",
  "utf8":1,
  "caseSensitive":1,
  "contextOperator":1,
  "dwdsThesaurus":0,
  "interpDelimiter":"\u001f",
  "tokenDelimiter":"\u001e",
  "allowUnsafeQueries":0,
  "indexPunctuation":1,
  "indexMorphPatterns":0,
  "indexChunks":0,
  //
  //-- index structure: bibliographic metadata
  "bibl":[
	{"name":"orig","builtin":1},
	{"name":"scan","builtin":1},
	{"name":"date","builtin":1},
	{"name":"page","builtin":1},
	{"name":"author", "visible":1, "size":4},
	//... other bibliographic fields ...
	{"name":"title", "visible":1, "size":4}
  	],
  //
  //-- index structure: break collections
  "breaks":[
	{"shortname":"s", "longname":"sentence", "size":2823},
	//... other break collections ...
	{"shortname":"textarea", "longname":"textarea", "size":4}
	],
  //
  //-- index structure: token-level indices
  "indices":[
	{"shortname":"w", "longname":"Token", "visible":1, "bigrams":2, "size":9369},
	{"shortname":"l", "longname":"Lemma", "visible":1, "size":5706},
	//... other token-level indices ...
	{"shortname":"p", "longname":"Pos", "visible":1, "size":53},
	],
  //
  //-- query operators: bibliographic expanders ("ExpandBibl" options)
  "xbibl":["xauthor",...]
  //
  //-- query operators: term expanders ("Expand" options)
  "expanders":["Token",...],
  //
  //-- user-supplied information ("ServerInfo" and "ServerInfoFile" options)
  "user":{"foo":"bar","baz":["bonk","boffo"]},
  }


For a branch server, the returned object has the form:

 {
  "name":"server",
  "version":"2.0.18-pre1",
  "corpora":[
 	{
 	 "name":"corpus1",
 	 //... information for subcorpus "corpus1" ...
	},
        //... information for other subcorpora ...
 	{
 	 "name":"corpusN",
 	 //... information for subcorpus "corpusN" ...
	}
  ]
 }

where each object in the "corpora" array is the associated subcorpus server's
response to an "info" request.
If the optional TIMEOUT parameter is specified, it should be an integer value indicating the
maximum time (in seconds) to wait for subcorpus responses; default=10.

Since v2.0.18,
user-supplied info since v2.0.34,
optional TIMEOUT parameter since v2.0.47.

=cut

##--------------------------------------------------------------
=pod

=head3 reload

 reload
 reload DEPTH

Requests re-loading local (sub)corpus data from disk.
If C<DEPTH> is present and non-zero, a receiving branch server
will send a C<reload> message with paramter C<DEPTH-1> to any subordinate
servers on the user's behalf; a C<DEPTH> parameter of -1 requests maximum depth.

Since v2.0.23, DEPTH parameter since v2.0.25.

=cut

##--------------------------------------------------------------
=pod

=head3 clear_cache

 clear_cache
 clear_cache DEPTH

Request that the receiving server immediately clear any in-memory query cache(s).
If C<DEPTH> is present and non-zero, a receiving branch server
will send a C<clear_cache> message with paramter C<DEPTH-1> to any subordinate
servers on the user's behalf; a C<DEPTH> parameter of -1 requests maximum depth.

Since v2.0.23, DEPTH parameter since v2.0.25.

=cut


##--------------------------------------------------------------
=pod

=head3 expand_terms

 expand_terms " \x01" PIPELINE "\x01" TERMS "\x01" TIMEOUT
 expand_terms " \x01" PIPELINE "\x01" TERMS "\x01" TIMEOUT "\x01" CORPUS

Requests online term expansion of the terms C<TERMS>
by the expansion pipeline C<PIPELINE>, which must be known to the leaf server chosen for expansion (see L<ddc_opt/Expand>).
C<TIMEOUT> is a request timeout in seconds.

For branch servers, if C<CORPUS> is specified, it should be the the name of an immediate subcorpus which should
be queried to perform the expansion.  If unspecified, the first registered subcorpus is queried.

Response data is of the form

 STATUS " " NTERMS "\n" DATA

where C<STATUS> is a decimal integer indicating the operation status (0 indicates success).
C<NTERMS> is the number of expanded terms being returned in the C<DATA> portion,
and C<DATA> is either an error message (just in case STATUS is non-zero) or a list of expanded terms
separated by TABs, newlines, and/or carriage returns (ASCII 0x09, 0x0a, 0x0d).

Since v2.0.0

=cut

##--------------------------------------------------------------
=pod

=head3 get_paradigm

 get_paradigm " " WORD "\x01" ILEMMATIZE " " ILANG

Request morphological analysis of the word C<WORD> using legacy built-in language-specific heuristics.
C<ILEMMATIZE> is a boolean integer; if true, only lemmatization is performed.
C<ILANG> is an integer indicating the built-in language rule-set to use; it should
be a valid MorphLanguageEnum value as defined in ${DDC_SRC}/src/common/utilit.h ;
currently recognized values are (0:unknown, 1:Russian, 2:English, 3:German, 4:Generic, 5:URL, 6:Digits).

Response is an HTML fragment.

Since v1.x

=cut

##--------------------------------------------------------------
=pod

=head3 ddc_close_socket

 ddc_close_socket

Dummy request used internally prior to ddc-v2.0.23 to avoid
annoying complaints unless each subcorpus socket gets exactly 2 messages per user request.
B<DANGEROUS> to use directly, can cause server lockup!

Since v2.0.0

B<OBSOLETE> since v2.0.23.

=cut

=head2 Branch-Server Messages

This section describes the messages accepted by DDC "branch" servers,
also known as "distributed" or "nonterminal" servers.  A branch server is not associated directly
with any single index, but functions as an aggregator for one or more subordinate
("leaf") servers.

Branch servers are prototypically used as the top-level instance for processing user
queries.  Prior to ddc-v2.1.0, only branch servers supported the following messages.

=head3 run_query

 run_query " " CORPUS "\x01" QUERY "\x01" FORMAT "\x01" OFFSET " " LIMIT " " TIMEOUT

Top-level user query request.

=over 4

=item CORPUS

is a vacuous parameter, by convention the string "Distributed" is used.

=item QUERY

is the user query in DDC syntax (see L<ddc_query(5)|ddc_query> for details).

=item FORMAT

is a string representing the data format to be returned by DDC.
Currently, DDC supports the following formats: "JSON", "TABLE", "TEXT", "HTML", or "DOCIDS".

=item OFFSET

is the index of the first hit to be retrieved, starting from 0 (zero).

=item LIMIT

is the maximum number of hits to be retrieved.

=item TIMEOUT

is the maximum number of seconds

=back

Server response depends on FORMAT.  In C<JSON> mode, the response data
for a traditional context-query is a JSON object of the form:

 {
   "istatus_" : 0,		//-- rsp. istatus_internal status code, 0:success
   "nstatus_" : 0,		//-- network status code, 0:success
   "error_" : null,		//-- error string, null:no error
   "nhits_" : 31,		//-- total number of hits
   "dhits_" : "17+4+10=31",	//-- distribution of hits over subcorpora
   "ndocs_" : 0,		//-- (?) number of documents containing hits (?)
   "ddocs_" : "0+0+0=0",	//-- (?) distribution of hit-documents over subcorpora (?)
   "end_" : 2,			//-- index of last returned hit
   "hits_" : [			//-- list of hits
     { 							//-- each hit is an object
       "meta_" : {					//-- hit.meta_: bibliographic metadata
            "file_" : "busch_max_1865.xml",		//-- indexed filename
            "indices_" : ["w","p","l"],			//-- indexed token fields for ctx_[1]
            "date_" : "1865",				//-- indexed date (decoded)
            "orig_" : "",
            "page_" : null,
            "scan_" : "",
            //... other indexed metadata fields go here ...
       },
       "ctx_": [				     	//-- hit.ctx_ provides result context
         [ "Ach",",","was","muß","man","oft",... ],	//-- hit.ctx_[0] is left extra-sentential context (strings only <v2.0.38)
         [						//-- hit.ctx_[1] is the hit sentence itself (structured tokens)
           [ 0, "Wie",      "PWAV",    "wie" ],		//-- tok[0] is match-ID, tok[1] is field meta_.indices_[0], etc
	   ...
	   [ 1, "Max",      "NE",      "Max" ],		//-- tok[0] is nonzero iff token matched a term in the user query
	   [ 0, "und",      "KON",     "und" ],
	   [ 2, "Moritz",   "NE",      "Moritz" ],	//-- user-supplied match-IDs are reported in tok[0]
	   ...
         ],
         [ ...,"heimlich","lustig","machen","." ]	//-- hit.ctx_[2] is right extra-sentential context (strings only <v2.0.38)
       ],
     },
     //... other hits go here ...
   ]
 }

As of v2.0.34, ddc supports user-supplied match-IDs via the C<=ID> query operator.
Matched tokens for which an explicit nonzero match-ID was supplied in the query
encode that ID as the first element of the returned token-array.

Prior to v2.0.38, ddc returned only raw token strings in the the extra-senential context
arrays hit.ctx_[0] and hit.ctx_[2].  As of v2.0.38, the tokens in these arrays
may themselves be array-encoded as for hit.ctx_[1], although sentence boundaries in
the extra-sential context arrays remain unencoded for maximum compatibility.
This behavior is disabled by default, but can be enabled by specifying the
C<--enable-json-deep-context> option to the F<configure> script when compiling ddc.

As of v2.0.23, ddc supports aggregate count-queries by means of the C<count()> operator.
If the requested C<QUERY> was such a count-query, the query response is slightly different:

=over 4

=item nhits_

indicates the best-guess maximum number of non-zero histogram bins for this query.
This number may be smaller than the actual number of non-zero histogram bins
if C<LIMIT> was less than the total number of non-zero bins in some subcorpus
and some non-zero bins occurred in more than one subcorpus:
such duplicate bins are merged by the branch server only, but only up to C<LIMIT>
are retrieved by the branch server for any query, so some uncertainty remains
regarding the status of duplicates among the bins beyond C<LIMIT>.

=item dhits_

is of the form "N1+N2+...=NTOTAL~NMAX", where the C<Ni> are the number of hits
(non-zero histogram bins) in the associated subcorpora, C<NTOTAL> is the total
number of non-zero histogram bins in any subcorpus (regardless of duplicates),
and C<NMAX> is the best-guess maximum number of non-zero histogram bins as reported
in C<nhits_>.

=item hits_

is not present.

=item counts_

is a JSON array of the form:

 [ BIN1, BIN2, ..., BINn ]

Each element C<BINi> of the C<counts_> array represents a single histogram bin
as a JSON array

 [ COUNT, KEY(s)... ]

where C<COUNT> is the total count for the bin in question and C<KEY(s)...>
are the key strings as requested in the C<QUERY> "#BY"-clause.

=back

Since v1.x, JSON format and error messages since v2.0.0.

=cut


##==============================================================
## Leaf Server Messages
=pod

=head2 Leaf Server Messages

This section describes the messages accepted by DDC "leaf" servers,
also known as "subcorpus", "local", or "terminal" servers.
A leaf server is directly associated with exactly one index on the local filesystem,
and has no subcorpora itself.

"Leaf-server messages" are requests sent by a branch server to its immediate
daughter subcorpora.  Prior to v2.1.0, a branch server could only have
leaf servers as immediate daughters (no logical corpus embedding).
As of v2.1.0, branch servers also support leaf-server requests, thus
allowing full "deep" corpus embedding; see L<ddc_cfg(5)|ddc_cfg>
for details.

=cut

##--------------------------------------------------------------
=pod

=head3 get_first_hits

 get_first_hits " " QUERY "\x01" TIMEOUT " " LIMIT

Requests subcorpus-local evaluation of the user query C<QUERY>.
C<TIMEOUT> is an operation timeout in seconds, and C<LIMIT> is the maximum
number of hits to evaluate.

If an error occurs, the response is of the form:

 STATUS " 0 0 0 0\n" ERROR

where C<STATUS> is a non-zero decimal integer error code, and C<ERROR> is a text string describing the error.

On success, responses have the form:

 STATUS " " MAXHIT " " NHITS " " NDOCS " " SORT " " HITIDS

where C<STATUS> is a decimal integer status, 0 (zero) for success,
C<MAXHIT> is the index of the last hit computed (?? see CConcHolder::GetHits(q, __EndHitNo__)),
C<NHITS> is the number of hits found (?? see CConcHolder::m_AllHitsCount),
C<NDOCS> is the number of relevant documents found (?? see CConcHolder::m_RelevantDocumentCount),
C<SORT> is a indicates whether and/or how the hits are to be sorted
(0: no sort, 1: ascending sort, -1: descending sort),
and C<HITIDS> is a TAB-separated list of C<NHITS> hit-identification triples (see CConcHolder::GetHitIds()),
each element of which has the form:

 INDEX " " ORDERID " " ORDER_STRING

where C<INDEX> is the query-dependent hit index,
C<ORDERID> is an integer, and C<ORDER_STRING> is a string.
Prior to ddc version 2.0.19,
C<ORDERID> was a global integer primary sort-key for the hit and C<ORDER_STRING>
was only non-trivially populated
if the query contained a context-dependend sort operation such as C<#left> or C<#right>,
and was otherwise assigned the literal string "E<lt>emptyE<gt>".

As of v2.0.19, C<ORDERID> is the literal string "-0", and
C<ORDER_STRING> is the (possibly empty) actual sort key for the hit.
If C<ORDER_STRING> is the literal string "<empty>", it is treated as an empty string for compatibility reasons.
C<ORDER_STRING> may also be a string of the form "#XXXXXXXX" representing a 32-bit integer
sort key in hexidecimal notation (msb order, high bit set for non-negative numbers only, no fill bits).

As of v2.0.23, ddc supports aggregate count-queries (by means of the C<count()> operator)
in addition to traditional "context" queries.  If the requested C<QUERY> was such a count-query,
then C<ORDER_STRING> is a "\x02"-separated list of count-key components, and C<INDEX> is the
total count of the associated histogram bin.

Since v1.x,
error message strings since v2.0.0,
count-queries since v2.0.23,
branch-server support since v2.1.0.

=cut

=pod

=head3 get_hit_strings

 get_hit_strings " " FORMAT "\x01" OFFSET " " LIMIT

Requests verbose hit strings for the current query
(assumedly the query itself was specified in the previous C<get_first_hits> request).
Hits are to be formatted in C<FORMAT>, which should be a format known to DDC.
C<OFFSET> is the offset of the first hit to return, starting from zero,
and C<LIMIT> is the maximum number of formatted hits to return.

If an error occurred, the response will be of the form:

 STATUS "\x01" "\n" ERROR

where C<STATUS> is a non-zero decimal integer error code (DDCErrorEnum InternalError),
and C<ERROR> is a text string describing the error.

On success, the response is of the form:

 STATUS "\x01" HIT_STRINGS "\x01"

where C<STATUS> is a decimal integer zero ("0")
and C<HIT_STRINGS> are the formatted hit strings, separated by "\x01".
By convention, each hit is terminated by "\n" and preceded by "\x01".
For "JSON" format hit strings, the first character of the first hit is a "[" character,
the final character of all non-final hits is a "," character, and the final character
of the final hit is a "]" character, so hits can be parsed as raw JSON data by removing
the initial C<STATUS> code and all "\x01" characters from C<HIT_STRINGS> before parsing.

An example response in JSON format is:

 0\x01[{"meta_":{"file_":"dannhauer_catechismus05_1654.xml",...},"ctx_":[[],[...],[]]},
 \x01{"meta_":{"file_":"frentzel_schauplatz_1744.xml",...},"ctx_":[[],[...],[]]},
 ...
 \x01{"meta_":{"file_":"busch_max_1865.xml",...},"ctx_":[[],[...],[]]},
 \x01{"meta_":{"file_":"frege_sinn_1892.xml",...},"ctx_":[[],[...],[]]}]
 \x01

Since v1.x,
JSON format and error messages since v2.0.0,
branch-server support since v2.1.0.

=cut

=head3 Socket Error! Servname not supported for ai_socktype

This message may be reported by branch server with
a misconfigured C<ddc_server.cfg> file.  In particular, if a subordinated server
is declared in the branch server's C<ddc_server.cfg> with no port number, or with
a colon separating the server address and the port number instead of a space, this
error message will be generated by any attempt to query the server.

=head3 std::bad_alloc

The server attempted to allocate too much memory while processing the
query.  Either reformulate your query to something less memory-intensive,
or provide more memory for the server machine / process.

=cut
